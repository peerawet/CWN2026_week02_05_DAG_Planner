hw06-churn-ml-pipeline

โจทย์: pipeline ทำนายลูกค้าเลิกใช้บริการ ตั้งแต่เตรียมข้อมูล เทรนโมเดล เก็บผลการทดลอง เปิดเป็น API และหน้า dashboard ติดตามผล

10 บล็อก dag: ไม่มี ERROR สายวิกฤต 9.6M tok แผน 4 agent ≈ 103.4 นาที วางแผนเมื่อ 2026-11-15 14:09
เกิดอะไรขึ้นบล็อกงานDAG · rank · สายวิกฤต Ganttเหตุผลตอนแตกบล็อกลดเหลือ 2 agent ไฟล์ยังต้องทำเอง

เกิดอะไรขึ้นบ้าง

ML pipeline ส่วนใหญ่ต้องเรียงกัน (ข้อมูล → สำรวจ → เตรียมข้อมูล → เทรน → API) จึงดึงงานที่แยกได้ออกมาทำขนาน: เลือก threshold ได้ทันทีหลังสำรวจข้อมูล ไม่ต้องรอเทรน และกำหนดโครง log กับหน้า dashboard จากรายชื่อฟีเจอร์ ไม่ต้องรอโมเดล

  1. แตกโจทย์เป็น 10 บล็อก บอกสกิล ขนาด ความยาก ไฟล์ผล และเกณฑ์เสร็จ ของทุกบล็อก → blocks.json
  2. สั่ง dag สกิลตรวจไฟล์บล็อก (วงวน id ซ้ำ สกิลที่ไม่รู้จัก) แล้วคิด rank และสายวิกฤต → ผ่าน ไม่มี ERROR · สายวิกฤต B02 → B03 → B04 → B05 → B07 → B10 ยาว 9.6M tok
  3. สั่ง plan --max-agents 4 KC-QUEST แจกบล็อกให้บัญชีจากโควตาสมมติ แล้วจำลองเวลา → แจกได้ 10/10 บล็อก · ใช้ agent พร้อมกันสูงสุด 3/4 · ≈ 103.4 นาที → dag.png gantt-plan.png PLAN.md
  4. สั่ง plan --max-agents 2 เป็นแผนแยกชื่อ hw06-churn-ml-pipeline-a2 จะได้ไม่ทับไฟล์ของข้อ 3 → แจกได้ 7/10 บล็อก → evidence/PLAN-max2.md
  5. หยุดที่แผน ไม่ได้สั่ง export run report ตามที่อาจารย์กำหนด จึงไม่ใช้โทเคนของทีม

โควตาที่ใช้เป็นค่าสมมติ --accounts yolo1:80,yolo2:60,cyolo1:90,cyolo2:70 สกิลจึงไม่เรียกบัญชีจริงเลย รันด้วย dagplan.py ตัวเดียวกับในสกิลบนเครื่อง Windows แทน docker exec เพราะตอนนั้น Docker Desktop ไม่ได้เปิดอยู่ (คำสั่งที่รันจริงอยู่ใน evidence/run.log)

สายวิกฤต

เริ่มที่บล็อก rank สูงสุด แล้วเดินไปหาบล็อกที่รออยู่ซึ่ง rank สูงสุดทีละก้าว: B02 (9.6) → B03 (9) → B04 (7.5) → B05 (6) → B07 (3) → B10 (1.5)

ความยาว = 0.6 + 1.5 + 1.5 + 3 + 1.5 + 1.5 = 9.6M tok เท่ากับ rank ของ B02 พอดี บล็อกบนสายนี้ช้าเท่าไร ทั้งโปรเจกต์ช้าเท่านั้น จึงได้เลือกบัญชีก่อน
