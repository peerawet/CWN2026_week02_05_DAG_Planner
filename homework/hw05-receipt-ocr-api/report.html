hw05-receipt-ocr-api

โจทย์: API อ่านใบเสร็จภาษาไทย (OCR) ด้วย FastAPI มีคิวงาน รันใน Docker และมีรายงานความแม่นยำจากชุดทดสอบ

10 บล็อก dag: ไม่มี ERROR สายวิกฤต 6.3M tok แผน 4 agent ≈ 63.0 นาที วางแผนเมื่อ 2026-11-15 14:09
เกิดอะไรขึ้นบล็อกงานDAG · rank · สายวิกฤต Ganttเหตุผลตอนแตกบล็อกลดเหลือ 2 agent ไฟล์ยังต้องทำเอง

เกิดอะไรขึ้นบ้าง

แยกเป็น 3 สายที่เริ่มพร้อมกันตั้งแต่นาทีแรก: สายโค้ด (โครง FastAPI → คิวงาน) สาย OCR (เลือก engine → ตัวอ่าน) และสายชุดทดสอบ (ภาพ → เฉลย) ทั้งสามมาบรรจบที่การวัดความแม่นยำและการรวม

  1. แตกโจทย์เป็น 10 บล็อก บอกสกิล ขนาด ความยาก ไฟล์ผล และเกณฑ์เสร็จ ของทุกบล็อก → blocks.json
  2. สั่ง dag สกิลตรวจไฟล์บล็อก (วงวน id ซ้ำ สกิลที่ไม่รู้จัก) แล้วคิด rank และสายวิกฤต → ผ่าน ไม่มี ERROR · สายวิกฤต B01 → B05 → B07 → B09 → B10 ยาว 6.3M tok
  3. สั่ง plan --max-agents 4 KC-QUEST แจกบล็อกให้บัญชีจากโควตาสมมติ แล้วจำลองเวลา → แจกได้ 10/10 บล็อก · ใช้ agent พร้อมกันสูงสุด 4/4 · ≈ 63.0 นาที → dag.png gantt-plan.png PLAN.md
  4. สั่ง plan --max-agents 2 เป็นแผนแยกชื่อ hw05-receipt-ocr-api-a2 จะได้ไม่ทับไฟล์ของข้อ 3 → แจกได้ 4/10 บล็อก → evidence/PLAN-max2.md
  5. หยุดที่แผน ไม่ได้สั่ง export run report ตามที่อาจารย์กำหนด จึงไม่ใช้โทเคนของทีม

โควตาที่ใช้เป็นค่าสมมติ --accounts yolo1:80,yolo2:60,cyolo1:90,cyolo2:70 สกิลจึงไม่เรียกบัญชีจริงเลย รันด้วย dagplan.py ตัวเดียวกับในสกิลบนเครื่อง Windows แทน docker exec เพราะตอนนั้น Docker Desktop ไม่ได้เปิดอยู่ (คำสั่งที่รันจริงอยู่ใน evidence/run.log)

สายวิกฤต

เริ่มที่บล็อก rank สูงสุด แล้วเดินไปหาบล็อกที่รออยู่ซึ่ง rank สูงสุดทีละก้าว: B01 (6.3) → B05 (5.7) → B07 (2.7) → B09 (2.1) → B10 (1.5)

ความยาว = 0.6 + 3 + 0.6 + 0.6 + 1.5 = 6.3M tok เท่ากับ rank ของ B01 พอดี บล็อกบนสายนี้ช้าเท่าไร ทั้งโปรเจกต์ช้าเท่านั้น จึงได้เลือกบัญชีก่อน
